How it works

JiraSlack

Team channels are where the real conversation happens during a release. "Oh, this isn't working?" "We need to build the export feature before launch."

That message is exactly the moment the issue should turn into a ticket, and exactly the moment it usually doesn't, because filing one means stopping the conversation to go do something else, so it depends on someone remembering.

JiraSlack reads the channel, classifies each message with an LLM, files a structured ticket, and asks a person first when it isn't confident enough to act alone.

StepWhat happens
01 Fetch + groupSlack messages and open Jira tickets are fetched in parallel, messages within a 5-minute window are grouped into one "block", the unit everything below operates on.
02 Duplicate gateThe block is embedded once and compared against cached ticket embeddings. Above 0.85 similarity, it's flagged as a duplicate and never reaches the model.
03 ClassifyThe only agentic step, and only one call, no loop. The LLM reads the block and returns a list of decisions (0 or more), one per actionable item, each with a type, priority, and confidence. Everything after that is deterministic code.
04 Route confidenceThe model's own confidence score is checked in plain code against two thresholds: auto-act, flag for review, or escalate.
05 Act / flag / escalateThe routed decision executes: file directly, file with a review label, or post a proposal to Slack for a human to approve.
06 Confirm to SlackEvery path ends with a message in the channel, a ticket link, a question, or a proposal, so nothing resolves silently.

This is the flow for one Slack block, not the system's architecture (components, storage, provider abstraction). For that: ARCHITECTURE.md.

Key trade-offs›
  • Duplicate detection: dense embedding similarity, not keyword match (misses paraphrases) or a hybrid dense+sparse setup like Continuum (added complexity this corpus doesn't need yet).
  • Ticket quality: a cross-family, calibrated LLM judge (OpenAI judging Claude's output), not BLEU/ROUGE, since there's no single correct ticket phrasing to match against.
My learnings›
Agent vs. deterministic code›
  • Started out wanting to build the entire flow as agentic, the goal was learning how tool-calling agents actually work, that was the exciting part. First version let the model decide as much as it could.
  • Then stepped back: what does this look like running unattended, not as a learning exercise?
    • Latency, every LLM call adds round-trip time; a loop can make several per message.
    • Cost, scales with volume, not with how interesting the problem is.
    • Reliability, a model's decision can vary run to run on the same input.
    • Debuggability, tracing why a loop chose a sequence of tools is harder than reading fixed branches.
  • Landed on the real discipline: the first question isn't "can an agent do this," it's "does this need one, or would a deterministic workflow get the same result cheaper, faster, more predictably."
  • Here, that meant an agentic core (classification) wrapped in deterministic guardrails (duplicate gating, confidence routing), not agent judgment applied everywhere.
Eval techniques›
  • Started wanting to just eyeball a few generated tickets and trust the model's own confidence at face value, fastest way to feel like it's working.
  • Then stepped back: that's not objective, doesn't scale, and different decisions need different proof.
    • Classification (type, priority) has one correct answer, eyeballing wastes the fact that ground truth exists.
    • Ticket quality (title, description) has no single correct phrasing, exact-match tooling would be wrong here.
    • Production behavior drifts over time, a one-time offline check doesn't catch that.
  • Landed on matching the eval method to the decision, not one technique for everything:
    • Golden dataset + direct comparison where ground truth exists (classification).
    • LLM-as-judge where it doesn't (ticket quality), but only trustworthy once cross-family and calibrated against known-good/known-wrong cases first, an uncalibrated judge is just an unverified opinion.
    • Human verification (Slack thumbs up/down) for a live, continuous signal that catches drift a static eval set can't, cheap per data point, feeds a rolling metric instead of requiring a full review.
How do we curate the memory?›
  • Curation starts before retrieval, at write time. Only blocks that end in a filed ticket become episodes. Duplicates, escalations, and clarification requests never get remembered, so noise never enters the store in the first place.
  • First retrieval approach: pre-inject the most similar past tickets into every single block. Simplest to build, most context available every time.
  • Stepped back: that means an embedding lookup and extra tokens on every block, including the ~80% that never needed past context at all. Second approach made that judgment the model's own, a search_memory tool it calls only when it says it's uncertain, cheaper on average, but it's a self-report: unverified, and inconsistent run to run on identical input.
  • Landed on something cheaper and deterministic instead: every block is already embedded once for the duplicate check, so that same vector is reused to score similarity against past episodes too, no second embedding call, no model decision involved. Only injected if the closest match clears a similarity threshold, so identical input always gets identical treatment, and checking costs nothing extra.
  • Relevance isn't the only thing being curated, amount, cost, and freshness all get a deliberate answer too:

Identifying failure points›
  • Started by walking the pipeline step by step and asking, at each one, what happens if this goes wrong.
  • Most of these failures don't look dramatic, a misclassified type, a vague description, nothing crashes or throws an error. But that's exactly what makes them dangerous: repeated enough times, they're what actually kills adoption, people quietly stop trusting the tickets and start re-checking everything by hand, which defeats the point of automating it at all.
  • So the discipline was treating every one of these as critical for the design, even though none of them "fail" in the traditional sense, and putting a guardrail behind each before shipping it.
